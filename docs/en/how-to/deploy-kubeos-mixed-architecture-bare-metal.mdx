# Deploy Mixed x86_64 and Arm Bare-Metal Clusters on KubeOS (Preview)

Use this guide to build Bare Metal clusters whose nodes run KubeOS (`alaudaos.k.25`) and mix x86_64 and Arm (aarch64) hosts, including in the same control plane. It covers the preview artifacts, the image and catalog layout that two architectures need, per-architecture registration, and the KubeOS-specific settings for `KubeadmControlPlane` and worker templates.

:::warning
**Preview build.** The provider and OS artifacts below are built from branches that are not merged or released yet. Use them for evaluation and testing only. The resource shapes on this page match the tested build; field names and defaults can change before release.
:::

Each archive is one OCI image layout with two images: the root filesystem that reprovisioning installs (`kubeos-rootfs`) and the live ISO image that `SeedImage` builds from (`kubeos-iso`). Unlike the SLE Micro archives, both images are named with the literal tag `baremetal`, not the archive name.

## How Architecture Is Resolved

Architecture is a property of each host, not of a pool or a cluster:

1. `elemental-register` reports the architecture it was built for as `${Runtime/Architecture}` (`amd64` or `arm64`). The register binary runs natively on the host, so this is the host architecture.
2. `MachineRegistration.spec.machineInventoryLabels` copies it to the `MachineInventory` label `os.baremetal.alauda.io/arch`.
3. When it reprovisions a host, the provider looks up `elemental-image-catalog` by `<kubernetes-version>_<arch>_<os-id>`, taking `<arch>` and `<os-id>` from that inventory's labels.

Because the lookup is per inventory, one `MachineInventoryPool` may hold x86_64 and Arm hosts together, and a `KubeadmControlPlane` may run on both. An inventory without the label resolves as `amd64`. An Arm host whose catalog key is missing stops in `Failed / Reason=ImageCatalogMiss`; it never falls back to an x86_64 image.

In a mixed pool you do not choose which architecture a new `Machine` lands on: the pool hands out its first available inventory. Kubernetes schedules workloads by the `kubernetes.io/arch` node label as usual. If you need a fixed number of Arm workers, give them their own pool and `MachineDeployment`.

## Prerequisites

- The platform was installed from the `hybrid` installer, and both provider plugins were installed from their `ALL` packages, on the bootstrap cluster and on `global`. See [Installing the global Cluster](../global/install.mdx) and [Prepare the global Cluster as a Management Cluster](../global/install.mdx#prepare-global-as-management-cluster).
- Any other plugin you install afterwards, for example `console` and `console-central`, also comes from its `ALL` package. A single-architecture package leaves its Pods unable to start on the other architecture's nodes.
- **Arm hosts expose SMBIOS.** `elemental-register` reads host identity with `dmidecode`, which needs `/sys/firmware/dmi/tables/`. UEFI Arm servers normally provide it; check once from the live ISO console with `ls /sys/firmware/dmi/tables/`. Without it, registration fails.
- **TPM.** Keep `emulate-tpm: false` only for hosts with a real TPM 2.0. For any host without one, including Arm hosts and VMs without a virtual TPM, set `emulate-tpm: true` with `emulated-tpm-seed: -1`, which derives a stable per-host seed from the SMBIOS system UUID.
- **The CNI interface has the same name on every host.** KubeOS keeps predictable interface names (for example `enp1s0`, not `eth0`), and `BaremetalCluster.spec.networkDevice` applies to the whole cluster. Confirm the name from each registered inventory's `spec.observedNetwork` before you create the cluster.

## Step 1: Import the OS Images for Both Architectures

Import both archives into the target platform registry. The two archives use the same image names (`kubeos-rootfs:baremetal` and `kubeos-iso:baremetal`), so import and push one architecture at a time, and give the pushed images an architecture-specific tag:

```bash
export OS_IMAGE_TAG="alaudaos-feat-kubeos-provider-integration.ku.202609281026-0"

for arch in x86_64 aarch64; do
  ctr -n bare-metal-os images rm kubeos-rootfs:baremetal kubeos-iso:baremetal 2>/dev/null || true
  ctr -n bare-metal-os images import --all-platforms --no-unpack "${OS_IMAGE_TAG}.${arch}.tar"
  for repo in kubeos-rootfs kubeos-iso; do
    ctr -n bare-metal-os images push --local --skip-verify \
      -u "<registry-username>:<registry-password>" \
      "<registry-address>/tkestack/${repo}:${OS_IMAGE_TAG}.${arch}" "${repo}:baremetal"
  done
done

for repo in kubeos-rootfs kubeos-iso; do
  curl -sk -u "<registry-username>:<registry-password>" \
    "https://<registry-address>/v2/tkestack/${repo}/tags/list"
done
```

Each list must show both the `.x86_64` and the `.aarch64` tag. Push with `ctr` as shown. Do not re-push the images with `docker push`: the KubeOS installer reads the image manifest as a single line, and a reformatted manifest makes the install fail only after the disk has been partitioned.

Run the import on a host with containerd, such as a `global` control-plane node, or on the bootstrap host during Global installation. The rest of [OS Images Imported and Image Catalog Populated](../create-cluster/bare-metal.mdx#os-images-and-image-catalog) applies unchanged.

## Step 2: Add a Catalog Entry per Architecture

Add one catalog entry for each architecture you deploy, with the three-segment key `<kubernetes-version>_<arch>_alaudaos.k.25`:

```bash
kubectl -n cpaas-system patch configmap elemental-image-catalog --type merge -p '{"data":{
  "v1.35.6-acp.1_amd64_alaudaos.k.25": "<registry-address>/tkestack/kubeos-rootfs:'"${OS_IMAGE_TAG}"'.x86_64",
  "v1.35.6-acp.1_arm64_alaudaos.k.25": "<registry-address>/tkestack/kubeos-rootfs:'"${OS_IMAGE_TAG}"'.aarch64"
}}'

kubectl -n cpaas-system get configmap elemental-image-catalog -o jsonpath='{.data}'
```

The version segment must equal `Machine.spec.version`, including the `v` prefix and the `-acp.1` suffix. A KubeOS host never falls back to a key without the OS segment, so every KubeOS entry needs all three segments. Point the catalog and the `SeedImage` at images from the same archive.

## Step 3: Register Hosts, One Registration per Architecture

`install.system-uri` names the root filesystem the live ISO installs, and that image is architecture-specific, so create one `MachineRegistration` and one `SeedImage` per architecture. The architecture label itself is identical in both: the register fills it in.

```yaml title="01-registration.yaml"
apiVersion: elemental.cattle.io/v1beta1
kind: MachineRegistration
metadata:
  name: <cluster-name>-registration-arm64      # repeat with an x86_64 variant
  namespace: cpaas-system
  labels:
    app.kubernetes.io/part-of: cluster-api-provider-baremetal
spec:
  machineName: "<cluster-name>-${System Information/UUID}"
  machineInventoryLabels:
    app.kubernetes.io/part-of: cluster-api-provider-baremetal
    pool.baremetal.alauda.io/eligible: "true"
    elemental.cattle.io/serial-number: "${System Information/Serial Number}"
    # OS identifier: selects the KubeOS host contract.
    os.baremetal.alauda.io/id: alaudaos.k.25
    # Architecture, reported by the register on every host.
    os.baremetal.alauda.io/arch: "${Runtime/Architecture}"
  machineInventoryAnnotations:
    elemental.cattle.io/machine-uuid: "${System Information/UUID}"
  config:
    elemental:
      install:
        device: /dev/vda                        # see Host Disk and Boot Preparation
        system-uri: <registry-address>/tkestack/kubeos-rootfs:<os-image-tag>.aarch64
        eject-cd: true
        reboot: true
      registration:
        emulate-tpm: true                       # false only with a real TPM 2.0
        emulated-tpm-seed: -1
---
apiVersion: elemental.cattle.io/v1beta1
kind: SeedImage
metadata:
  name: <cluster-name>-registration-arm64-iso
  namespace: cpaas-system
  labels:
    app.kubernetes.io/part-of: cluster-api-provider-baremetal
spec:
  type: iso
  baseImage: <registry-address>/tkestack/kubeos-iso:<os-image-tag>.aarch64
  registrationRef:
    apiVersion: elemental.cattle.io/v1beta1
    kind: MachineRegistration
    name: <cluster-name>-registration-arm64
    namespace: cpaas-system
  # Required for KubeOS: kubeos-iso is built FROM scratch. linux/amd64 for the x86_64 variant.
  targetPlatform: linux/arm64
  size: 20Gi
  cleanupAfterMinutes: 120
  cloud-config:
    name: kubeos-live-registry
    stages:
      network:
        # The live ISO installs from the platform registry, which uses a self-signed certificate.
        - files:
            - path: /etc/containers/registries.conf.d/99-platform.conf
              permissions: 0644
              content: |
                [[registry]]
                location = "<registry-address>"
                insecure = true
```

Differences from the SLE Micro registration in [Create Cluster → Step 1](../create-cluster/bare-metal.mdx#step-1-machineregistration-seedimage):

| Field | KubeOS value | Why |
|---|---|---|
| `machineInventoryLabels["os.baremetal.alauda.io/id"]` | `alaudaos.k.25` | Without it the provider renders the SLE Micro contract. |
| `machineInventoryLabels["os.baremetal.alauda.io/arch"]` | `"${Runtime/Architecture}"` | Per-host catalog lookup. |
| `install.system-uri` | Architecture-specific `kubeos-rootfs` image | The KubeOS installer pulls the root filesystem from the registry. |
| `install.snapshotter` | Omit | Ignored by the KubeOS installer. |
| `SeedImage.spec.targetPlatform` | `linux/arm64` or `linux/amd64` | Required: the ISO image has no shell of its own. |
| `SeedImage.spec.cloud-config` `stages.boot` `COS_STATE` sizing | Omit | KubeOS uses fixed A/B root partitions and `/persist`, not `COS_STATE`. |
| `stages.network` registry entry | Add | The live ISO must trust the platform registry before it installs. |

The `tkestack/*` repositories allow anonymous pulls, so the live ISO needs no registry login. The KubeOS archives listed above give the live ISO a working `/etc/resolv.conf`, so registration by the platform domain name works without extra configuration.

Boot each host from the ISO of its architecture, then check the labels:

```bash
kubectl -n cpaas-system get machineinventories.elemental.cattle.io \
  -L os.baremetal.alauda.io/arch -L os.baremetal.alauda.io/id \
  -o custom-columns='NAME:.metadata.name,ARCH:.metadata.labels.os\.baremetal\.alauda\.io/arch,PLAN:.status.plan.state,NIC:.spec.observedNetwork.interfaces[0].name'
```

Every inventory must show its architecture (`amd64` or `arm64`), `PLAN` `Applied`, and the same interface name.

## Step 4: Create the Cluster

Follow [Create Cluster → Steps 2 to 4](../create-cluster/bare-metal.mdx#step-2-pools). The pool may list x86_64 and Arm inventories together:

```yaml
apiVersion: infrastructure.cluster.x-k8s.io/v1beta1
kind: MachineInventoryPool
metadata:
  name: <cluster-name>-control-plane-pool
  namespace: cpaas-system
spec:
  clusterName: <cluster-name>
  machineInventories:
    - name: <x86_64-inventory>
      hostname: <cluster-name>-cp-1
    - name: <arm64-inventory-1>
      hostname: <cluster-name>-cp-2
    - name: <arm64-inventory-2>
      hostname: <cluster-name>-cp-3
```

KubeOS needs three additions to the manifests on that page:

1. **`BaremetalCluster.spec.networkDevice`** set to the interface name from Step 3. An empty value means `eth0`, which does not exist on KubeOS, and the cluster stops at `NetworkDeviceReady=False`.
2. **The flexvolume directory in `KubeadmControlPlane`.** `/usr` is read-only on KubeOS, so `kube-controller-manager` cannot create its default flexvolume host path and `kubeadm init` never completes. Move the directory under `/opt`:

   ```yaml
   kubeadmConfigSpec:
     clusterConfiguration:
       controllerManager:
         extraArgs:
           flex-volume-plugin-dir: "/opt/libexec/kubernetes/kubelet-plugins/volume/exec/"
     initConfiguration:
       nodeRegistration:
         kubeletExtraArgs:
           volume-plugin-dir: "/opt/libexec/kubernetes/kubelet-plugins/volume/exec/"
     joinConfiguration:
       nodeRegistration:
         kubeletExtraArgs:
           volume-plugin-dir: "/opt/libexec/kubernetes/kubelet-plugins/volume/exec/"
   ```

3. **The same `volume-plugin-dir` in the worker `KubeadmConfigTemplate`**, under `spec.template.spec.joinConfiguration.nodeRegistration.kubeletExtraArgs`. The rest of the worker template is as in [Managing Nodes on Bare Metal](../manage-nodes/bare-metal.mdx#step-3-configure-bootstrap-template).

These apply to the `KubeadmControlPlane` of the `global` cluster as well when its nodes run KubeOS.

## Verification

Check which catalog key the provider used for each host:

```bash
kubectl -n cpaas-system logs deploy/cluster-api-provider-baremetal-manager --all-containers \
  | grep 'resolved OS image' | grep -o '"machineInventory": "[^"]*"\|"catalogKey": "[^"]*"'
```

x86_64 inventories resolve `v1.35.6-acp.1_amd64_alaudaos.k.25` and Arm inventories `v1.35.6-acp.1_arm64_alaudaos.k.25`. Then check the nodes in the workload cluster:

```bash
kubectl get nodes -L kubernetes.io/arch
kubectl get pods -A -o wide | grep -v -E 'Running|Completed'
```

## Common Failure Modes

| Symptom | Cause | Action |
|---|---|---|
| `BaremetalMachine` `Failed / ImageCatalogMiss` naming `..._arm64_alaudaos.k.25` | No Arm catalog entry. | Add the entry (Step 2), then delete the `Machine` so its owner recreates it. |
| An inventory has no `os.baremetal.alauda.io/arch` label | The ISO carries a register older than this preview. | Rebuild the ISO from the listed `kubeos-iso` images. |
| Live ISO console: `registering machine: ... lookup <domain> on [::1]:53 ... connection refused` | KubeOS archive built before `ku.202609281026-0`: its live ISO has no `/etc/resolv.conf`. | Use the listed archives. With an older archive, add `commands: [ln -sfn /run/NetworkManager/resolv.conf /etc/resolv.conf]` to the `stages.network` step of the `SeedImage`. |
| Registration fails on an Arm host before any inventory appears | No SMBIOS tables, or `emulate-tpm: false` without a TPM. | Check `/sys/firmware/dmi/tables/`; set `emulate-tpm: true` with `emulated-tpm-seed: -1`. |
| `kubeadm init` never completes; `kube-controller-manager` reports `mkdir /usr/libexec/kubernetes: read-only file system` | Flexvolume directory not moved. | Add the Step 4 settings. |
| Pods of one plugin stay in `ImagePullBackOff` only on Arm nodes | The plugin was installed from a single-architecture package. | Install the plugin's `ALL` package. |

## Tested Topology

The preview was validated on 2026-09-28 with virtual machines on one Layer-2 network:

- `global`: control plane of two x86_64 hosts and one Arm (Kunpeng 920) host, plus one Arm worker, installed from `installer-core-v4.4.0-hybrid.tar`.
- Workload cluster: control plane of one x86_64 and two Arm hosts in one pool.

Both clusters reached `Running` on the platform with every Pod healthy on both architectures, and every host resolved the catalog key of its own architecture.
