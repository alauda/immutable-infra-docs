# Upgrading the global Cluster

This document describes how to upgrade a `global` cluster that runs on Immutable Infrastructure. Upgrades replace nodes with new Alauda OS images managed by the Cluster API provider; in-place node upgrades are not used.

For a Huawei DCS `global` cluster, review [Alauda OS and Provider Compatibility](../overview/providers/huawei-dcs.mdx#alauda-os-and-provider-compatibility) before selecting the target DCS Provider package and Alauda OS image.

## When to Use This Path

Choose this upgrade path when:

- The `global` cluster was originally installed on Immutable Infrastructure. See [Installing the global Cluster](./install.mdx).
- Your infrastructure is one of the documented providers: Huawei DCS, VMware vSphere, Huawei Cloud Stack, or Bare Metal when provider `v1.0.0` or later is included in the installed release.

For traditional-OS `global` clusters, use <ExternalSiteLink name="acp" href="/upgrade/upgrade_global_cluster.html" children="the standard upgrade path" /> instead.

## Two-Phase Upgrade Overview

Like workload clusters, the `global` cluster on Immutable Infrastructure follows a two-phase upgrade.

1. **Phase 1 — ACP Core and Distribution Version**: prepare artifacts and plugin packages, then use CVO to move the global tier to the target Distribution Version. The ACP product documentation owns this procedure; see <ExternalSiteLink name="acp" href="/upgrade/pre-upgrade.html" children="Pre-Upgrade Preparation" /> and <ExternalSiteLink name="acp" href="/upgrade/upgrade_global_cluster.html" children="Upgrade the global cluster" />.
2. **Phase 2 — Kubernetes and OS Image**: nodes are replaced with new Alauda OS images that contain the target Kubernetes version. This document focuses on Phase 2 for the `global` cluster.

<Directive type="info" title="Phase 1 Compatibility">
  Before starting Phase 2, verify that every workload cluster falls within the Compatible Versions matrix of the target Distribution Version. Workload clusters that are out of range must be upgraded first.
</Directive>

## Common Prerequisites

- The `global` cluster has completed Phase 1 (Distribution Version upgrade).
- An etcd backup of the `global` cluster has been taken and verified.
- On Huawei DCS, VMware vSphere, and Huawei Cloud Stack, the `global-sa` and `global-proxy` Secrets hold the same ServiceAccount signing key and front-proxy CA as the control plane nodes. [Step 1](#check-sa-and-front-proxy-secrets) checks this and repairs a `global` cluster that was installed with ACP v4.3.0.
- The target row in [OS Support Matrix](../overview/os-support-matrix.mdx) is available, and its Kubernetes version, CoreDNS tag, etcd tag, and Kube-OVN chart are staged, together with the Alauda OS image published for that release.
- The previous machine templates and bootstrap templates are retained until Phase 2 is verified.
- A maintenance window plan that accounts for rolling control plane replacement.
- For cross-version upgrades that span more than one Kubernetes minor, the intermediate-version Core images and OS images are pre-staged. See [Cross-Version Upgrade Preparation](../upgrade-cluster/index.mdx#cross-version-preparation).

## Procedure

After installation, the Cluster API controllers that manage the `global` cluster run on the `global` cluster itself. Use the `global` kubeconfig for the `kubectl` commands in this procedure.

<Directive type="warning" title="Required when the target is Kubernetes 1.35">
  In Kubernetes 1.35, kubelet credential verification can apply to images that are already present on a node. On the hop to Kubernetes 1.35 or later, add `imagePullCredentialsVerificationPolicy: NeverVerify` to the kubelet patch used by every replacement node. Update the control-plane file in the same `KubeadmControlPlane` edit as `spec.version`. For workers, create a new `KubeadmConfigTemplate` with the updated patch and switch `MachineDeployment.spec.template.spec.bootstrap.configRef.name` in the same edit as the version. Do not add this parameter for Kubernetes 1.34 or earlier. See [Required kubelet patch for Kubernetes 1.35](../upgrade-cluster/index.mdx#kubernetes-1-35-kubelet-patch).
</Directive>

### Step 1 — Check the ServiceAccount and Front Proxy Secrets \{#check-sa-and-front-proxy-secrets}

Run this step on Huawei DCS, VMware vSphere, and Huawei Cloud Stack before any control plane node is replaced. Bare Metal skips it.

A replacement control plane node does not copy the Kubernetes ServiceAccount signing key or the front-proxy CA from the node it replaces. It receives them from two Cluster API Secrets in the `cpaas-system` namespace:

| Secret | Data key | File on every control plane node |
| :--- | :--- | :--- |
| `global-sa` | `tls.crt` | `/etc/kubernetes/pki/sa.pub` |
| `global-sa` | `tls.key` | `/etc/kubernetes/pki/sa.key` |
| `global-proxy` | `tls.crt` | `/etc/kubernetes/pki/front-proxy-ca.crt` |
| `global-proxy` | `tls.key` | `/etc/kubernetes/pki/front-proxy-ca.key` |

The ACP v4.3.0 installer did not import these two Secrets into the `global` cluster, so `KubeadmControlPlane` generated new ones that the running control plane nodes do not use. Installers from ACP v4.3.1 onward import them. On a `global` cluster installed with ACP v4.3.0 whose control plane has not been replaced since, the first replacement node signs and verifies ServiceAccount tokens with a different key from the other nodes. A request then fails with `401 Unauthorized` whenever its token reaches an API server that uses the other key. Kubeadm Provider v1.0.9 and later hold the next control plane replacement until platform-registry has been reinstalled for the new set of nodes. The platform-registry installation Job on the replacement node is rejected in the same way, so the next control plane `Machine` stays in `Deleting` and the rollout stops.

The check is read-only. Run it on every Huawei DCS, VMware vSphere, and Huawei Cloud Stack `global` cluster, whichever release installed it, and repair the Secrets before Step 4 applies the updated manifest.

<Directive type="info" title="Disaster recovery pairs">
  Run this step on each `global` cluster against that cluster's own API server, after the etcd synchronization plugin has been uninstalled as the DR upgrade procedure requires, and before the control plane of that cluster is replaced. The primary and standby clusters have different keys. Never copy files or Secrets from one cluster to the other.
</Directive>

Run the commands from a secured host that has `kubectl`, `base64`, `sha256sum`, and an administrator kubeconfig for the `global` cluster. Keep shell tracing disabled. The commands read the node files through `kubectl exec` into the `kube-apiserver` static Pod, which mounts `/etc/kubernetes/pki` from the node, and print only the first 16 characters of SHA-256 digests. They never print key material.

#### List the Control Plane Machines

```shell
export KUBECONFIG="<path-to-global-kubeconfig>"

kubectl -n cpaas-system get machines \
  -l cluster.x-k8s.io/cluster-name=global,cluster.x-k8s.io/control-plane \
  -o custom-columns='MACHINE:.metadata.name,NODE:.status.nodeRef.name,VERSION:.spec.version,PHASE:.status.phase'
kubectl -n cpaas-system get secret global-sa global-proxy --show-managed-fields \
  -o jsonpath='{range .items[*]}{.metadata.name}:{range .metadata.managedFields[*]} {.manager}{end}{"\n"}{end}'
```

Before Step 4, every control plane `Machine` shows the current Kubernetes version. In the second output, a Secret whose only field manager is `manager` was generated by `KubeadmControlPlane`, and a Secret that the installer imported also lists `kubectl-client-side-apply`. This is only a hint; the comparison below decides.

#### Compare the Secrets With the Control Plane Nodes

```shell
set -euo pipefail
set +x
export KUBECONFIG="<path-to-global-kubeconfig>"

# Secret, data key, and the node file that must hold the same bytes.
PKI_ITEMS="global-sa:tls.crt:sa.pub global-sa:tls.key:sa.key global-proxy:tls.crt:front-proxy-ca.crt global-proxy:tls.key:front-proxy-ca.key"

secret_sha() {
  kubectl -n cpaas-system get secret "$1" -o "jsonpath={.data.${2//./\\.}}" |
    base64 -d | sha256sum | cut -c1-16
}

node_sha() {
  kubectl -n kube-system exec "kube-apiserver-$1" -- \
    cat "/etc/kubernetes/pki/$2" | sha256sum | cut -c1-16
}

CONTROL_PLANE_NODES="$(kubectl -n cpaas-system get machines \
  -l cluster.x-k8s.io/cluster-name=global,cluster.x-k8s.io/control-plane \
  -o jsonpath='{range .items[*]}{.status.nodeRef.name}{"\n"}{end}')"

secrets_differ=false
nodes_differ=false
for item in ${PKI_ITEMS}; do
  IFS=: read -r secret key file <<< "${item}"
  expected="$(secret_sha "${secret}" "${key}")"
  reference=""
  for node in ${CONTROL_PLANE_NODES}; do
    actual="$(node_sha "${node}" "${file}")"
    printf '%-19s secret=%s node=%s %s\n' "${file}" "${expected}" "${actual}" "${node}"
    reference="${reference:-${actual}}"
    [ "${actual}" = "${reference}" ] || nodes_differ=true
    [ "${actual}" = "${expected}" ] || secrets_differ=true
  done
done

if [ "${nodes_differ}" = true ]; then
  echo "RESULT: the control plane nodes do not hold the same files"
elif [ "${secrets_differ}" = true ]; then
  echo "RESULT: global-sa or global-proxy differs from the control plane nodes"
else
  echo "RESULT: consistent"
fi
```

If `kubectl exec` reports that `cat` is not found, read the same files on each node with `sudo cat` over SSH instead.

Act on the last line of the output:

| Result | Meaning | Action |
| :--- | :--- | :--- |
| `RESULT: consistent` | Every control plane node holds the files stored in the Secrets. | Continue with Step 2. |
| `RESULT: global-sa or global-proxy differs from the control plane nodes` | The control plane nodes agree with each other, but the Secrets hold other keys. The ACP v4.3.0 installer leaves a `global` cluster in this state. | [Repair the Secrets](#repair-sa-and-front-proxy-secrets), then run the comparison again. |
| `RESULT: the control plane nodes do not hold the same files` | The control plane is already split. | Do not choose a node as the source. If a control plane rollout is in progress, follow [Recover a Rollout Stopped by Mismatched Keys](#recover-mismatched-keys). Otherwise, contact technical support. |

#### Repair the Secrets \{#repair-sa-and-front-proxy-secrets}

Repair the Secrets only after the comparison reported `RESULT: global-sa or global-proxy differs from the control plane nodes`. Set `SOURCE_NODE` to any node name from the comparison output, because all of them hold the same files. Set `BACKUP_DIR` to a directory on the secured host that does not exist yet.

```shell
set -euo pipefail
set +x
umask 077
export KUBECONFIG="<path-to-global-kubeconfig>"
export SOURCE_NODE="<control-plane-node-name>"
export BACKUP_DIR="<new-backup-directory>"

mkdir "${BACKUP_DIR}"
for secret in global-sa global-proxy; do
  printf '{"data":%s}\n' \
    "$(kubectl -n cpaas-system get secret "${secret}" -o jsonpath='{.data}')" \
    > "${BACKUP_DIR}/${secret}.json"
done

WORK_DIR="$(mktemp -d)"
trap 'rm -rf "${WORK_DIR}"' EXIT
for file in sa.pub sa.key front-proxy-ca.crt front-proxy-ca.key; do
  kubectl -n kube-system exec "kube-apiserver-${SOURCE_NODE}" -- \
    cat "/etc/kubernetes/pki/${file}" > "${WORK_DIR}/${file}"
done

data_patch() {
  printf '{"data":%s}\n' "$(kubectl create secret generic data-patch \
    --from-file=tls.crt="$1" --from-file=tls.key="$2" \
    --dry-run=client -o jsonpath='{.data}')"
}
data_patch "${WORK_DIR}/sa.pub" "${WORK_DIR}/sa.key" > "${WORK_DIR}/global-sa.json"
data_patch "${WORK_DIR}/front-proxy-ca.crt" "${WORK_DIR}/front-proxy-ca.key" \
  > "${WORK_DIR}/global-proxy.json"

kubectl -n cpaas-system patch secret global-sa \
  --type merge --patch-file "${WORK_DIR}/global-sa.json"
kubectl -n cpaas-system patch secret global-proxy \
  --type merge --patch-file "${WORK_DIR}/global-proxy.json"
```

The commands save the current `data` of both Secrets in `BACKUP_DIR`, read the four files from `SOURCE_NODE` into a temporary directory that is removed on exit, and replace only `data.tls.crt` and `data.tls.key` of each Secret. The Secret type, labels, and owner reference stay as they are. Run the comparison again; it must report `RESULT: consistent`.

The files in `BACKUP_DIR` contain the private keys that `KubeadmControlPlane` generated. Keep them only on the secured host, and delete them after the upgrade is verified.

To undo the repair before Step 4 starts the rollout, restore the saved data:

```shell
export KUBECONFIG="<path-to-global-kubeconfig>"
export BACKUP_DIR="<backup-directory-of-the-repair>"

kubectl -n cpaas-system patch secret global-sa \
  --type merge --patch-file "${BACKUP_DIR}/global-sa.json"
kubectl -n cpaas-system patch secret global-proxy \
  --type merge --patch-file "${BACKUP_DIR}/global-proxy.json"
```

Do not restore the saved data after a replacement control plane node has joined. That node uses the repaired keys, and restoring the saved data would split the control plane again.

#### After the Rollout

When Step 5 completes, run the comparison again. It must report `RESULT: consistent` for every replacement node. In a DR pair, also run it on the standby `global` cluster after the etcd synchronization plugin has been reinstalled. If it reports a difference there, the plugin is overwriting the standby Secrets with those of the primary. Contact technical support before you replace any control plane node of that cluster.

### Step 2 — Upgrade Kube-OVN

Read the **kube-ovn (chart)** value from the target OS Support Matrix row, then follow the shared [provider-version-specific Kube-OVN procedure](../upgrade-cluster/index.mdx#upgrade-kube-ovn-before-the-control-plane) with `<cluster-name>` set to `global`.

That procedure first checks the installed provider revision, then selects the supported new or legacy flow, handles the Kube-OVN chart-name boundary at `v4.4`, and verifies the chart name, target revision, installed revision, phase, and conditions. Use the `global` kubeconfig for both the provider and `cni-kube-ovn` `AppRelease` checks. Do not begin control-plane replacement until all shared verification criteria pass.

### Step 3 — Update the global Cluster Manifest

Update the Cluster API manifests of the `global` cluster to reference the new Alauda OS image and Kubernetes version. The manifest fields to update are provider-specific.

<Tabs>
  <Tab label="Huawei DCS">

For DCS, create new immutable infrastructure templates instead of editing templates that are already referenced by running machines.

Update the control plane resources:

- Create a new `DCSMachineTemplate` for the target image and set `spec.template.spec.vmTemplateName` to the Alauda OS template that matches the target Kubernetes version.
- Keep preserved node-local data, including `/var/cpaas`, in `DCSIpHostnamePool.spec.pool[].persistentDisk`. Do not move preserved disks back into `DCSMachineTemplate`.
- Set `KubeadmControlPlane.spec.version` to the target Kubernetes version.
- Set the CoreDNS and etcd image tags in `KubeadmControlPlane.spec.kubeadmConfigSpec.clusterConfiguration` from the same OS Support Matrix row.
- When the target is Kubernetes 1.35 or later, update the control-plane kubelet patch in `KubeadmControlPlane.spec.kubeadmConfigSpec.files` in the same manifest edit.
- Point `KubeadmControlPlane.spec.machineTemplate.infrastructureRef.name` to the new `DCSMachineTemplate`.
- Keep `KubeadmControlPlane.spec.rolloutStrategy.rollingUpdate.maxSurge: 0` when the cluster uses pool-managed persistent disks.

Update worker node resources:

- Create a new worker `DCSMachineTemplate` with the target `vmTemplateName`.
- Set each `MachineDeployment.spec.template.spec.version` to the target Kubernetes version.
- When the target is Kubernetes 1.35 or later, create a new worker `KubeadmConfigTemplate` with the required kubelet patch and point `MachineDeployment.spec.template.spec.bootstrap.configRef.name` to it.
- Point each `MachineDeployment.spec.template.spec.infrastructureRef.name` to the new worker `DCSMachineTemplate`.
- Keep each `MachineDeployment.spec.strategy.rollingUpdate.maxSurge: 0` when the worker pool uses pool-managed persistent disks.

Pool-managed persistent disks are declared on the IP pool, not on the machine template:

```yaml
apiVersion: infrastructure.cluster.x-k8s.io/v1beta1
kind: DCSIpHostnamePool
metadata:
  name: <global-pool-name>
  namespace: cpaas-system
spec:
  pool:
    - ip: <node-ip>
      hostname: <node-hostname>
      persistentDisk:
        - slot: 0
          quantityGB: 40
          datastoreName: <datastore-name>
          path: /var/cpaas
          format: xfs
          mountOptions:
            - defaults
```

Use `isThin` only when the DCS environment requires an explicit thin-provisioning value. If omitted, the provider does not send `isThin` and DCS uses the platform default. New persistent volumes are created as independent persistent normal volumes.

Use the IP pool status to confirm that preserved disks are detached from old VMs and attached to replacement VMs during the rolling replacement.

  </Tab>

For vSphere, create new immutable infrastructure templates instead of editing templates that are already referenced by running machines.

Update the control plane resources:

- Export the current `VSphereMachineTemplate`, give the copy a new name, remove server-generated metadata and `status`, and set `spec.template.spec.template` to the VM template created in vSphere from the Alauda OS image published for the target ACP release.
- Preserve the existing vCenter, folder, datastore, network, clone-mode, CPU, memory, and disk configuration unless the release procedure explicitly changes it. Leave `spec.template.spec.providerID` unset.
- Keep preserved node-local data, including `/var/cpaas`, in `VSphereMachineConfigPool.spec.configs[].persistentDisks[]`; do not move it into the machine template.
- Set `KubeadmControlPlane.spec.version`, CoreDNS, and etcd tags from the same OS Support Matrix row.
- When the target is Kubernetes 1.35 or later, update the control-plane kubelet patch in `KubeadmControlPlane.spec.kubeadmConfigSpec.files` in the same manifest edit.
- Point `KubeadmControlPlane.spec.machineTemplate.infrastructureRef.name` to the new `VSphereMachineTemplate`.
- Keep `KubeadmControlPlane.spec.rolloutStrategy.rollingUpdate.maxSurge: 0` when the control plane pool uses fixed slots or pool-managed persistent disks.

Update worker node resources:

- Create a new worker `VSphereMachineTemplate` with the target VM template and the retained provider configuration.
- Set each `MachineDeployment.spec.template.spec.version` to the target Kubernetes version.
- When the target is Kubernetes 1.35 or later, create a new worker `KubeadmConfigTemplate` with the required kubelet patch and point `MachineDeployment.spec.template.spec.bootstrap.configRef.name` to it.
- Point each `MachineDeployment.spec.template.spec.infrastructureRef.name` to the new worker `VSphereMachineTemplate`.
- Keep each `MachineDeployment.spec.strategy.rollingUpdate.maxSurge: 0` when the worker pool uses fixed slots or pool-managed persistent disks.

`VSphereMachineTemplate.spec.template.spec` is immutable. Keep the previous control-plane and worker templates until the new rollout is verified.

For HCS, create new immutable infrastructure templates instead of editing templates that are already referenced by running machines.

Update the control plane resources:

- Create a new `HCSMachineTemplate` for the target image and set `spec.template.spec.imageName` to the Alauda OS image that matches the target Kubernetes version.

- Set `KubeadmControlPlane.spec.version` to the target Kubernetes version.

- Keep `KubeadmControlPlane.spec.rolloutStrategy.rollingUpdate.maxSurge: 0` when the control plane pool uses pool-managed persistent disks.

- Create a new worker `HCSMachineTemplate` with the target `imageName`.
- Set each `MachineDeployment.spec.template.spec.version` to the target Kubernetes version.
- When the target is Kubernetes 1.35 or later, create a new worker `KubeadmConfigTemplate` with the required kubelet patch and point `MachineDeployment.spec.template.spec.bootstrap.configRef.name` to it.
- Point each `MachineDeployment.spec.template.spec.infrastructureRef.name` to the new worker `HCSMachineTemplate`.
- Keep each `MachineDeployment.spec.strategy.rollingUpdate.maxSurge: 0` when the worker pool uses pool-managed persistent disks.

Pool-managed persistent disks are declared on the machine configuration pool, not on the machine template:

```yaml
apiVersion: infrastructure.cluster.x-k8s.io/v1beta1
kind: HCSMachineConfigPool
metadata:
  name: <global-pool-name>
  namespace: cpaas-system
  labels:
    cluster.x-k8s.io/cluster-name: global
spec:
  configs:
    - hostname: <node-hostname>
      networks:
        - subnetName: <subnet-name>
          ipAddress: <node-ip>
      persistentDisks:
        - slot: 0
          size: 100
          type: SSD
          mountPath: /var/cpaas
          format: xfs
          mountOptions:
            - defaults
            - noatime
```

Do not treat HCS `dataVolumes[]` as preserved state during node replacement. This rolling upgrade workflow supports highly available control planes that can replace `HCSMachineTemplate` and `KubeadmControlPlane` references while `HCSMachineConfigPool` retains enough fixed identities and persistent disk slots for the rollout. Single-control-plane HCS clusters, including a `global` cluster with one control plane node, are not supported by this rolling upgrade workflow. Use an alternative documented procedure, recreate the control plane with immutable templates, or consult the out-of-band migration guide or support before proceeding.

This YAML workflow requires Bare Metal provider `v1.0.0` or later. Use it only after that provider package and the target OS Support Matrix row are available in the installed release. Before editing Cluster API resources, confirm that the provider `AppRelease` requested and installed revisions match and its chart phase is `Success`.

Import the target release's Bare Metal OS images into the `global` cluster's registry and add the target Kubernetes version to its `elemental-image-catalog`, as described in [OS Images Imported and Image Catalog Populated](../create-cluster/bare-metal.mdx#os-images-and-image-catalog). Neither the provider plugin nor the Distribution Version upgrade adds the version for you. In a DR pair, do this on both `global` clusters. Then verify the catalog:

```shell
kubectl --kubeconfig <global-kubeconfig> -n cpaas-system \
  get configmap elemental-image-catalog -o yaml
```

The target version must appear as a key with a reachable base-image reference. A replacement `Machine` created while the key is missing leaves its `BaremetalMachine` in `Failed` with `Reason=ImageCatalogMiss`, and adding the key afterwards does not recover it. The Bare Metal provider resolves the replacement image from `Machine.spec.version`; a Kubernetes-only upgrade does not require a new `BaremetalMachineTemplate` unless the control plane or workers must move to a different `MachineInventoryPool`.

Update the existing `KubeadmControlPlane` manifest with values from the same OS Support Matrix row. Preserve all fields not shown here:

```yaml
spec:
  version: <target-kubernetes-version>
  rolloutStrategy:
    rollingUpdate:
      maxSurge: 0
  kubeadmConfigSpec:
    clusterConfiguration:
      dns:
        imageTag: <target-coredns-tag>
      etcd:
        local:
          imageTag: <target-etcd-tag>
```

Retain the existing `spec.kubeadmConfigSpec.files` entries. For Kubernetes 1.35 or later, update the existing `kubeletconfiguration0+strategic.json` entry in that list as documented above; do not replace the list with an empty value.

For each worker `MachineDeployment`, set the target Kubernetes version and keep `maxSurge: 0`. When the target is Kubernetes 1.35 or later, first create a new immutable `KubeadmConfigTemplate` containing the required kubelet patch, then reference it in the same manifest change:

```yaml
spec:
  strategy:
    rollingUpdate:
      maxSurge: 0
  template:
    spec:
      version: <target-kubernetes-version>
      bootstrap:
        configRef:
          name: <target-kubeadm-config-template>
```

Omit the `bootstrap.configRef` change for an earlier target when no bootstrap setting changes. Apply the complete retained manifests in Step 4. The provider deletes each old machine, cleans its inventory, allocates an available inventory from the same pool, and writes a `reprovision` plan for the target image.

</Tabs>

### Step 4 — Apply the Updated Manifest

Apply the updated manifest against the `global` cluster.

```shell
kubectl --kubeconfig <global-kubeconfig> apply -f <updated-manifest>
```

The Cluster API provider begins replacing control plane and worker nodes by using the new image. When `maxSurge: 0` is set, each old node is drained and deleted before its replacement can reuse the same fixed identity, IP address, or preserved disk.

### Step 5 — Monitor the Rolling Replacement

Watch the rolling replacement until all control plane and worker nodes have been replaced.

```shell
kubectl --kubeconfig <global-kubeconfig> get machines -A -o wide
kubectl --kubeconfig <global-kubeconfig> get kubeadmcontrolplane -A
```

The upgrade is complete when every `Machine` reports the new Kubernetes version and `Phase: Running`, and the `KubeadmControlPlane` reports `Ready: True` against the new version.

## Verification

After the rolling replacement finishes, verify that the upgraded `global` cluster is healthy.

```shell
kubectl --kubeconfig <global-kubeconfig> get nodes -o wide
kubectl --kubeconfig <global-kubeconfig> get clusterversionshadow -o yaml
kubectl --kubeconfig <global-kubeconfig> get pods -n cpaas-system
```

All nodes must report the new Kubernetes version, the `ClusterVersionShadow` must reflect the target Distribution Version, and core platform pods must be `Running`.

## Failed Upgrades \{#failed-upgrades}

An upgrade cannot be rolled back: do not set the versions or the templates back to their previous values. Restoring an etcd backup does not return a cluster to an earlier version either. Fix the reported cause and the rollout continues; if the cause cannot be fixed, contact technical support.

On Huawei DCS clusters that use pool-managed persistent disks, check `DCSIpHostnamePool.status.persistentDiskStatus` before you delete or recreate machines, and do not delete retained DCS volumes that are listed in `DCSIpHostnamePool.spec.pool[].persistentDisk`.

If the rollout stops after the first control plane node has been replaced and platform components report `401 Unauthorized`, see [Recover a Rollout Stopped by Mismatched Keys](#recover-mismatched-keys).

### Recover a Rollout Stopped by Mismatched Keys \{#recover-mismatched-keys}

This applies to Huawei DCS, VMware vSphere, and Huawei Cloud Stack when the Secrets in [Step 1](#check-sa-and-front-proxy-secrets) were not repaired before the rollout of a `global` cluster installed with ACP v4.3.0.

Symptoms:

- The first replacement control plane node joins, but the next control plane `Machine` stays in `Deleting`. Its `PreDrainDeleteHookSucceeded` condition is `False` with reason `WaitingExternalHook`, and it still carries the `pre-drain.delete.hook.machine.cluster.x-k8s.io/platform-registry-rollout-gate` annotation.
- Platform components intermittently log `401 Unauthorized` or `the server has asked for the client to provide credentials`, and the `platform-registry` installation Job fails.
- The comparison in Step 1 reports `RESULT: the control plane nodes do not hold the same files`. The replacement nodes, whose `Machine` shows the target version, share one set of digests that equals the Secrets. The nodes that have not been replaced share another set.

Do not delete `Machine` objects, remove the hook annotation, or skip the rollout gate with `cpaas.io/skip-platform-registry-rollout-gate`, even when a `RolloutGateFailed` event suggests it. A rollout that finishes on the generated keys invalidates every token signed with the original key, including long-lived ServiceAccount token Secrets. Instead, put the original keys back on the replacement nodes. Run this recovery together with technical support.

1. Confirm that at least one node that has not been replaced is `Ready`, and that all nodes that have not been replaced show the same digests in the comparison. A node whose `Machine` is `Deleting` but has not been drained yet counts as not replaced. If these nodes differ from each other, stop and contact technical support.

2. [Repair the Secrets](#repair-sa-and-front-proxy-secrets) with `SOURCE_NODE` set to a node that has not been replaced, so that the remaining replacement nodes receive the original keys.

3. On each replacement node, restore the four files from `SOURCE_NODE`, renew the front-proxy client certificate that the generated CA signed, and restart `kube-apiserver` and `kube-controller-manager`. The commands connect as the `boot` user, which has passwordless `sudo` on the node.

   ```shell
   set -euo pipefail
   set +x
   umask 077
   export KUBECONFIG="<path-to-global-kubeconfig>"
   export SOURCE_NODE="<control-plane-node-name-not-replaced>"
   export TARGET_NODE="<replacement-control-plane-node-name>"
   export TARGET_HOST="<replacement-control-plane-node-address>"
   PKI_FILES="sa.pub sa.key front-proxy-ca.crt front-proxy-ca.key"
   CRICTL="sudo crictl --runtime-endpoint unix:///run/containerd/containerd.sock"

   WORK_DIR="$(mktemp -d)"
   trap 'rm -rf "${WORK_DIR}"' EXIT
   for file in ${PKI_FILES}; do
     kubectl -n kube-system exec "kube-apiserver-${SOURCE_NODE}" -- \
       cat "/etc/kubernetes/pki/${file}" > "${WORK_DIR}/${file}"
   done

   ssh "boot@${TARGET_HOST}" \
     'sudo cp -a /etc/kubernetes/pki "/etc/kubernetes/pki-backup-$(date +%Y%m%d%H%M%S)"'
   for file in ${PKI_FILES}; do
     ssh "boot@${TARGET_HOST}" "sudo tee /etc/kubernetes/pki/${file} > /dev/null" \
       < "${WORK_DIR}/${file}"
   done
   ssh "boot@${TARGET_HOST}" 'sudo kubeadm certs renew front-proxy-client'

   for name in kube-apiserver kube-controller-manager; do
     id="$(ssh "boot@${TARGET_HOST}" "${CRICTL} ps -q --name '^${name}\$'")"
     ssh "boot@${TARGET_HOST}" "${CRICTL} stop ${id}"
   done

   until kubectl --server "https://${TARGET_HOST}:6443" get --raw /readyz > /dev/null 2>&1; do
     sleep 5
   done
   kubectl -n kube-system exec "kube-apiserver-${TARGET_NODE}" -- \
     cat /etc/kubernetes/pki/front-proxy-client.crt > "${WORK_DIR}/front-proxy-client.crt"
   openssl verify -CAfile "${WORK_DIR}/front-proxy-ca.crt" "${WORK_DIR}/front-proxy-client.crt"
   ```

   The commands keep the previous `/etc/kubernetes/pki` of the node in `/etc/kubernetes/pki-backup-<timestamp>` on that node, wait until its API server is ready again, and end with `openssl verify` printing `OK` for the renewed front-proxy client certificate. The kubelet restarts the stopped containers with the restored files.

4. Check that every API server accepts the tokens that every other API server issues. Set `CONTROL_PLANE_ADDRESSES` to the addresses of all control plane nodes.

   ```shell
   set -euo pipefail
   set +x
   umask 077
   export KUBECONFIG="<path-to-global-kubeconfig>"
   export CONTROL_PLANE_ADDRESSES="<control-plane-address-1> <control-plane-address-2> <control-plane-address-3>"

   WORK_DIR="$(mktemp -d)"
   trap 'rm -rf "${WORK_DIR}"' EXIT
   kubectl -n kube-system get configmap kube-root-ca.crt \
     -o jsonpath='{.data.ca\.crt}' > "${WORK_DIR}/ca.crt"
   for issuer in ${CONTROL_PLANE_ADDRESSES}; do
     printf 'Authorization: Bearer %s\n' "$(kubectl --server "https://${issuer}:6443" \
       -n default create token default --duration=10m)" > "${WORK_DIR}/header"
     for verifier in ${CONTROL_PLANE_ADDRESSES}; do
       printf 'token issued by %s, sent to %s: ' "${issuer}" "${verifier}"
       curl -sS -o /dev/null -w '%{http_code}\n' --cacert "${WORK_DIR}/ca.crt" \
         -H @"${WORK_DIR}/header" "https://${verifier}:6443/version"
     done
   done
   ```

   Every line must end with `200`. A `401` means that the issuing and the receiving API server still use different keys.

5. Remove the generated front-proxy CA from the trust bundle that aggregated API servers read. While a replacement node ran with that CA, the API servers added it to the `kube-system/extension-apiserver-authentication` ConfigMap, and they keep merged entries until the certificates expire. Delete the ConfigMap; each API server re-creates it from its own files within seconds.

   ```shell
   kubectl -n kube-system delete configmap extension-apiserver-authentication
   kubectl -n kube-system get configmap extension-apiserver-authentication
   ```

   Repeat the second command until it returns the ConfigMap.

6. Run the comparison in Step 1 again. It must report `RESULT: consistent`.

7. Watch the rollout continue. The rollout gate removes its hook after the platform-registry `AppRelease` is ready for the current control plane nodes.

   ```shell
   kubectl -n cpaas-system get events --field-selector involvedObject.kind=Machine | grep PlatformRegistry
   kubectl -n cpaas-system get machines \
     -l cluster.x-k8s.io/cluster-name=global,cluster.x-k8s.io/control-plane -w
   ```

   If the platform-registry `AppRelease` is still not ready 30 minutes after the comparison reports `RESULT: consistent`, contact technical support.

8. After the rollout completes, clean up:

   - Pods that received their ServiceAccount token from a replacement API server before step 3 keep failing with `401` until the kubelet refreshes the token, which happens within about an hour. Delete such Pods to recover sooner.
   - A long-lived ServiceAccount token Secret of type `kubernetes.io/service-account-token` that was created while the controller manager of a replacement node held the leader lease is signed with the generated key. If a component that uses such a Secret still fails with `401`, remove the `token` key from the Secret, and the token controller signs a new token.
   - Delete the `/etc/kubernetes/pki-backup-<timestamp>` directories on the replacement nodes and the `BACKUP_DIR` of the Secret repair. Both contain generated private keys.
